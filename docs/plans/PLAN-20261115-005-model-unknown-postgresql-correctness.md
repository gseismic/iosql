## 当前依据和约束

- 前轮在隔离 PostgreSQL 14 复现五项问题；当时现有相关测试为 106 passed，未覆盖这些反例。本轮以当前代码重新验证。
- PostgreSQL 新连接为 autocommit，`commit=False` 由引擎维护显式事务和库级共享租约；不能把丢失的事务悄悄转换为自动提交。失败清理不得掩盖原始异常，也不能由普通引擎提前结束迁移发布器持有的事务。
- delete 的既有约定是提交同连接的待处理事务；参数错误仍应在删除前拒绝。
- `insert_all` 按整批列并集写入，缺列补 NULL；`upsert_all` 按输入顺序合并字段，缺字段保留、显式 None 清空。两者语义不可混淆。
- 文本 calendar 时间要求统一格式；查询应保持列上的直接范围谓词，不能为修正精度而对列逐行转换，损失分区裁剪。
- 分区锁应覆盖布局读取和写入，且排斥 ATTACH/DETACH 等布局变更；保留普通读取及分区契约检查。

## 方案与取舍

1. 事务丢失时使用现有 `UnsafeOperation` 明确拒绝续写并清理状态；正常未持有事务的连接仍可重连。统一写事务的开始、提交、回滚和租约释放，检查提交与回滚本身失败的路径。选择明确失败而非自动重放，避免掩盖事务丢失或重复执行。
2. delete 与 delete_all 复用写事务入口；迁移专用连接仍由发布器统一提交。
3. 重复主键在提交给 ON CONFLICT 前按最后输入行取值；由数据库按目标列类型识别冲突身份，保持分页后的最终结果一致，避免仅比较 Python 原始值漏掉 SQL 类型归一后的重复。字段级 upsert 继续保留字段合并语义。
4. 增加内部查询边界归一扩展点；文本时间下界向上对齐到存储精度，上界向下对齐，保留原生 DATE/TIMESTAMP、纯日期和其他后端既有语义。拒绝通过截断下界扩大结果集。
5. 使用与分区布局 DDL 冲突、但允许普通 SELECT 的父表锁，并在真实并发会话中验证阻塞和解锁。

## 2026-11-15 15:58 实施复核补充

模型：Codex（基于 GPT-6，实际模型 ID 未提供）；范围仍为 WORKTREE，基准提交不变。新增真实 PostgreSQL 回归在修改实现前得到 21 failed、4 passed，覆盖五个反例及以下必要的相邻路径。

- 延迟约束在 COMMIT 时失败，原实现会保留事务标记和共享租约；断连后的 rollback 还会覆盖原始错误。统一事务清理一并修复。
- `upsert_all` 全局按 Python 原始主键和字段组重排，会把 PostgreSQL 等价键（例如 BIGINT 的 `1` 与 `'1'`）按错误顺序合并。改为按输入顺序处理连续的相同字段集合，每组交给同一批量 SQL 冲突处理；同字段批次仍批量执行，交替字段形状可能产生更多 SQL，但不牺牲输入顺序和缺字段保留语义。
- 原生父表锁选用 SHARE UPDATE EXCLUSIVE。PostgreSQL 14 的 LOCK 权限规则要求表级 UPDATE、DELETE 或 TRUNCATE 之一（官方依据：`https://www.postgresql.org/docs/14/sql-lock.html`）；仅 SELECT/INSERT 的非所有者角色无法取得这个锁。为保留布局校验到写入的保护，不降级为弱锁、不自动授权；返回有指引的库级异常，同步 README/skill 权限说明及对应回归。非所有者具备所需锁权限后仍不需要所有者身份进行已有摘要分区的写入。
