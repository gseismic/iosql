## 目标、范围和边界

- 加快用户的 SQLite 目录库到 Parquet 目录库的大规模迁移，覆盖源表统计与复制、Parquet 批量写入、分区元数据查询和目标验证的实际热点。
- 保持现有公开 API、CLI 参数、迁移结果、冲突模式、源行数独立校验、缺失文件报错、资源预算、锁和安全发布协议。源表尚未完全统计时不得展示虚假的总行数；预览和其他引擎继续保持既有行为。
- 测试使用独立临时库和对用户源库的只读抽样；不操作用户正式目标、不重启真实迁移、不提交或推送。

## 当前状态与方案

- 用户源表有 9,984 个六小时物理分区；现有流程先对所有文件执行 `COUNT(*)`，然后再次打开它们复制，进度中途无法开始写入。其旧格式清单没有可直接信任的逐文件行数。
- Parquet 每批逐行执行 DuckDB `executemany`。同一个真实分区的 5 万行、同样事务和主键约束下，直接使用列式 `UNNEST` 约 0.55 秒，原方式约 3.62 秒，完整结果集差集为空；单次局部测试不代表端到端加速倍数。PyArrow 在本机可用，但不是项目必需依赖，不能让优化依赖它。
- 方案比较：新增强制 PyArrow 依赖会改变安装契约；只增加批大小不能解决逐行调用；选择 DuckDB 自带的列式输入，并对无法证明类型语义等价的输入和冲突模式使用既有路径。可评估可选 PyArrow 加速，但必须有无需可选依赖的快速路径。
- 对 SQLite → Parquet 的正式迁移，按文件读取时在同一只读 SQLite 查询及快照中取得独立物理行数并复制，避免全库预扫描后再遍历。文件总数已知但全表行数在最后一个文件前未知，CLI 如实展示已复制行数和已检查文件；最终结果仍填入独立源行数。空文件、段文件、缺失文件、行丢失、取消和单连接预算必须有明确验证。干运行及其他迁移路径保持预扫描。
- 分区是否存在用精确索引查询或本次暂存上下文内的安全复用替代反复物化全量列表；目标结构检查应降低连接和重复遍历成本，但不能跳过必要的损坏检测、清单验证或发布前校验。

## 实施步骤

1. 建立代表性性能基线，验证 DuckDB 列式输入与原始路径在数值、文本、二进制、NULL、异常和冲突模式上的等价边界。
2. 实施 Parquet 列式批量写入和分区元数据查询优化；对不满足明确条件的输入使用旧路径。
3. 实施 SQLite → Parquet 的逐文件统计与复制，以及总行数未知时的 CLI 进度；保留最终源计数、目标计数和独立校验。
4. 优化目标验证的重复连接或遍历；保留损坏、清单和发布一致性检查。
5. 补充针对风险的测试，运行迁移、Parquet、SQLite、CLI、安全发布和资源限制回归；使用独立真实样本或合成库比较端到端耗时和结果。复核代码与现有工作区改动，记录结果和遗留项。

## 实施前自查、风险与完成标准

- 列式输入不得改变整数精度、浮点值、NULL、二进制或字符串；批内和跨数据片重复主键以及 ignore/replace/upsert 必须维持旧语义；不安全输入回退而不吞掉真实异常。
- 独立源计数必须与数据读取处于同一 SQLite 快照；不能用已复制行数冒充源计数。任一源文件缺失、损坏或读取中断不得发布目标；目标含额外历史数据及所有迁移模式按原契约处理。
- 迁移失败的阶段、异常、部分结果和恢复行为保持一致；CLI 标准输出仍为 JSON，进度只写标准错误；内存随批大小受限，单连接和读取流释放正确。
- 验证包括空表、不同分区/段、schema 演进、数据异常、冲突、干运行、可选依赖缺失、目标损坏、跨后端和安全发布。性能数字同时记录数据规模、缓存和环境，不能用微基准代替完整链路。
