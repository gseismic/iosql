## 目标、范围与约束

用户反馈选择表进入 Data 很慢，希望支持大表按需加载。进入 Data 时优先获取契约和当前页；准确行数、库级统计和需要扫描物理文件的分区详情由用户按需触发。保持既有 keyset 排序、过滤、翻页、只读权限和服务端接口；不改动数据库文件或后台运行的用户进程。

不根据分区文件名假设历史数据均按现行分区契约存储，也不改变全局排序和 NULL 检测语义。首页查询仍可能因分区数、排序和存储速度而耗时；本次不承诺消除这些查询自身的成本。

## 当前状态与依据

Data 已按 200 行 keyset 分页，但启动自动执行所有表的 `/stats`，成功后继续执行 `/segments`；Data 请求成功后还自动执行 `/count`。旧式 SQLite 分区的 `/segments` 会逐文件计算列的 min/max 和行数，与数据查询争用 I/O。用户库为 6 小时分区、13 列；对运行中服务的温缓存单次首页 `/rows` 测量约 0.19 秒，不能据此推断冷启动耗时或断定唯一瓶颈。

## 实施步骤

1. 移除启动期间自动统计；总览清楚区分未加载、进行中和失败，提供单表和全库行数统计、按表加载分布与失败重试。
2. Structure 在用户进入时按需获取分区明细，复用同一 `/segments` 请求用于分布及明细，保留 obsolete 切换和失败重试。
3. Data 默认只请求当前数据页；通过明确操作统计当前筛选结果，按条件缓存，筛选、翻页、刷新及切换页面时避免过期响应覆盖。
4. 更新现有使用说明及服务端文档字符串，明确统计何时执行以及 legacy 分区可能需要扫描文件；更新静态资源版本。
5. 自查并运行浏览器回归、Web 接口回归和 JavaScript 语法检查，测试初始网络请求、筛选计数、分页、统计重试、延迟响应和 Structure 的共享请求。

## 验证方式与完成标准

- 启动和进入 Data 不自动请求 `/stats`、`/segments`、`/count`；下一页及过滤后仍可正确读取，按需统计给出准确结果。
- 总览与 Structure 保留统计功能，状态与重试准确；同一 Structure 加载过程只请求一次普通 segment 明细。
- 真实浏览器与既有 Web 回归通过，不修改用户数据。记录能实际完成的运行中用户库验证，区分暖缓存与冷缓存。

## 风险与回滚

自动统计改为按需操作会改变数字出现的时机，须在界面与使用说明标明；按需请求仍可能耗时。异步请求需去重并隔离过期响应，避免显示错误计数。变更集中于前端、服务端说明、测试与文档，回滚时只撤销本次差异，保留先前未提交修改。
