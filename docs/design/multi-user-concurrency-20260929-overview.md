# iosql 多用户同时读写：当前保证与演进设计

- 日期：2026-09-29
- 对应计划：`docs/dev/PLAN-072-full-review-fixes-and-concurrency.md`
- 适用对象：同一台机器上多个 `Database` 实例、线程或进程访问同一个 SQLite 目录库。

## 现有结构和本轮实测

一个逻辑表由表级 `meta.sqlite3` 和多个 `data/*.sqlite3` 文件组成。每个 SQLite 文件启用 WAL；`_db_parts_condition` 与连接池预算解决单进程连接生命周期，过去的 `_compact_lock` 只属于一个 `Table` 对象。写入 segment 时，代码先选择当前 segment，再写数据文件和 manifest。这几个步骤跨文件、跨事务。

本轮先在未加跨进程锁的代码上让两个进程读到同一个剩余容量为 1 的 segment，随后同时写入：两个 `write()` 均成功，物理文件有 3 行，manifest 却记录 2 行，`validate(deep=True)` 报 `row_count_mismatch`。这证明仅有 SQLite 单文件写锁和对象内 `RLock` 不足以保护复合写入。

本轮增加表目录中的 `.iosql.write.lock`，在同机多个协作进程之间用 OS 文件锁串行化同表的写入、`upsert_all`、`compact`、`cleanup_obsolete`、删除、索引和契约元数据修改。锁对同对象嵌套调用可重入。进程退出时 OS 释放锁；异常路径显式释放。两个竞争回归：

1. 两进程同时写同一 segment，最终 3 行且深度校验通过。
2. 一个进程在 `compact` 读完旧 segment 后暂停，另一个进程尝试写入；最终 2 行都可见且深度校验通过。未加锁时这类时序可能使后写行随旧 segment 被标记 obsolete 而不可见。

另一次三进程探针同时运行两个不同分区写者与一个读者：写者和读者均无异常，最终 101 行、分区 `[0, 10]`，深度校验通过；读者循环查询在运行中观察到 1 至 11 行。这个探针证明该有限工作负载可运行，不构成所有读操作的全局快照证明。

## 当前可依赖的边界

| 场景 | 当前行为 |
| --- | --- |
| 同进程多线程写同表 | 表对象锁和连接租约保护内部状态；本轮文件锁也覆盖独立 `Database` 实例。 |
| 同机多进程写同表 | 遵守 iosql API 的复合写入按表串行；不同表可并行。不同分区仍暂按同表串行，以换取 manifest 一致性。 |
| 读与写同时进行 | 单个 SQLite 文件的 WAL 允许读写并行；读游标在其文件内持有自己的语句快照。跨文件/分区查询没有统一时刻的快照。 |
| `compact` 与写 | 两者持有同一表级文件锁；本轮的确定性竞争测试通过。 |
| 进程崩溃或断电 | 文件锁可自动释放，但数据文件和 manifest 分别提交，可能留下行数/状态不一致；应先运行 `validate(deep=True)` 再恢复写入。 |
| `rename`、`restore`、在线备份、`repartition_to` 与活跃读写 | 不提供无停机原子切换。迁移或替换目录时应停止相关进程，关闭连接，完成操作后重开。备份恢复前后的深度校验能发现一类损坏，不代表并发复制具有统一快照。 |
| 多台机器共享同一目录 | 不在当前保证内。SQLite 官方明确 WAL 的共享内存机制要求参与进程在同一台主机。 |
| 多用户 Web 服务 | `web` 的 `--write` 是进程级开关，没有内建用户身份、角色和审计；需要独立服务层认证授权后才能向多个不互信用户开放。 |

SQLite 官方说明：WAL 支持读者和写者并行，但同一时间单文件仅一个写者；WAL 不支持跨网络文件系统；多个数据库文件的更新不能整体原子提交。iosql 的表级锁只保证**协作进程的执行顺序**，不能弥补跨文件崩溃原子性。[SQLite WAL 文档](https://sqlite.org/wal.html)、[ATTACH 文档](https://sqlite.org/lang_attach.html)。

## 推荐使用方式

1. 同机受信任的多个进程可并发调用常规 `write()`/`select()`。每次应用启动前对需要严格一致性的表运行深度校验；出现校验错误应停止写入并从完整备份恢复或人工修复 manifest。
2. 对外服务采用单个受控 API 入口，统一认证、授权、限流和审计。客户端不要直接共享目录。`iosql web` 只作本机运维界面；使用 `--allowed-host` 仅解决 Host 路由，不提供身份认证。
3. `rename`、`restore`、物理清理、在线备份与重分区安排维护窗口，先停写并关闭其他读连接。跨文件查询若要求同一时间点结果，应在上层冻结写入或使用静态快照副本。

## 后续演进路径

**阶段 1：确定可靠恢复流程。** 将表级写入记录为可重放操作日志，记录操作 ID、目标文件、预期 manifest 变更和状态；启动时检查未完成操作并修复或隔离。深度校验增加自动修复建议，但删除/重建数据前必须保留原文件。补断电/进程强杀故障注入测试。

**阶段 2：不可变 segment 与代际提交。** 新数据写临时文件、校验、原子改名后，再在一个表级 manifest 事务中发布新 generation；读者固定 generation，旧文件待无读者时清理。这样可让读者在维护时继续读取已发布代际，并消除先改数据再改 manifest 的覆盖窗口。跨多个表仍需上层协调。

**阶段 3：按分区并行写。** 在 generation 协议成立后引入分区级锁与 manifest 的冲突重试，避免当前整表串行；若业务要求全局主键唯一性，需要全局索引或统一写入服务。基准须覆盖热点分区、冷分区、混合查询和连接数上限。

**阶段 4：一致性快照 API。** 为跨分区读取提供显式快照代际或冻结写入的读取事务；在此之前，不应将 `select()`、流式 `iter_rows()` 或导出称为全库线性一致读取。
