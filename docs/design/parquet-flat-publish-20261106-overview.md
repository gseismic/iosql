## 目标和边界

Parquet 目标的普通建表、写入及跨后端迁移应产生相同的根目录结构：`库/表/meta.sqlite3` 和 `库/表/data/`。支持新库、已有库、部分选表、多个表和现有写入模式；其他表的数据保留。SQLite 目标与 PostgreSQL 目标不改变。

根据用户授权，新发布不要求兼容向旧代目录布局的 Parquet 目标再次迁入；遇到这样的目标应在准备暂存之前报错。旧代目录仍可作为源读取。用户指定的唯一现存库以单独的一次性脚本整理，不自动改动其他库。

## 方案比较

1. 沿用完整代目录和外部指针：多表发布只需切换一次指针，但同类数据库按创建方式显示不同目录，复制时还依赖外部物理路径控制记录。
2. 将暂存表逐个直接覆盖根目录：目录直观，但崩溃后可能留下混合版本，替换已有 SQLite 元数据文件还会与空闲 WAL 连接冲突。
3. 使用持久提交决定及恢复屏障切换表数据：根目录结构保持一致。保留已有表元数据文件 inode，用 SQLite backup 事务性更新其内容；新表整体移入根目录。iosql 协作访问由租约和恢复屏障保护，未选表不移动。

采用方案 3。多表文件系统变更本身不是单一原子操作；一致性仅对遵守 iosql 库级租约的访问成立，不扩展到原始文件读写或旧客户端。

## 状态和恢复

1. 独占源库和目标库，检查目标契约；在目标文件系统准备完整暂存，复制选中表并按需核验行数、深度检查文件。
2. 持久化候选任务标记、目标表/元数据/数据目录身份和 `FLAT_COMMIT_DECIDED`。此前失败不发布新表；此后读取、写入先取得独占租约恢复。
3. 对新表，整体移动暂存目录到根目录。对已有表，将原 `data` 移入本任务退休空间，将新 `data` 移入原表目录，并使用 SQLite backup 更新原 `meta.sqlite3`。每一步核对设备与 inode；重放以身份和路径判断已完成的移动。
4. 深度校验发布后的选中表，再将 generation 和 `COMMITTED` 一起写入控制记录。后续操作通过 generation 刷新已打开的对象。
5. 已提交暂存优先在独占租约内移到父目录的任务专属退休目录，解锁后清理。目标根为独立挂载点时，POSIX 使用固定到已打开目录的描述符清理；平台不支持时保留暂存并警告。

任何身份不符、路径异常或恢复写入错误都必须保留恢复屏障并报告 `MigrationRecoveryRequired`。失败期间不能清除待恢复暂存或把部分数据作为已提交结果。默认工作区在目标文件系统；跨盘显式工作区在提交决定之前复制到目标文件系统。

## 验证和已知边界

- 临时库覆盖新目标、已有目标空闲元数据连接、未选表、后续写入、不同文件系统的暂存、目标根内工作区，以及逐步故障和重复恢复。
- 用户 Z1 的 NTFS/FUSE 文件系统已用于独立临时库演练；常见的 Linux `RENAME_NOREPLACE` 在该文件系统上不可用，一次性整理使用独占预留目录并核验身份。正式发布的目标均在库级独占租约内检查冲突。
- 测试没有验证 Windows 原机和断电行为；Windows 仍不承诺与 POSIX 目录 `fsync` 等价的持久性。外部非协作写入、多人共享目录的恶意路径替换不由该协议保护。
- 用户现存目标在整理前后核对了 21,906 个数据文件的相对路径、设备、inode、大小和修改时间，三个样本文件的 SHA-256 一致。该核验不是对全部数据文件重新计算内容哈希。
