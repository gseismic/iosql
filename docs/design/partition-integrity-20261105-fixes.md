## 使用场景与不变量

1. 初次声明、写入并重开分区表：保留表契约，按相同规则路由与裁剪。
2. 同一进程或重开后声明不同分区：有既有物理布局时拒绝原地切换；通过显式迁移写入新目标。
3. 空表显式使用 `force_partition`：可更改尚无物理分区的数据布局；相同分区的声明和新建目标保留兼容。
4. 低层 `insert_all`：初次未声明表可指定分区；已有契约或物理布局后不得绕过兼容性检查。
5. PostgreSQL 多实例并发、旧表重开：即使原表没有持久化 iosql 契约，也必须依据全部原生子分区验证粒度；写入前在事务内串行化并重查，不能仅依赖实例内缓存。
6. 多日 calendar 跨年：沿用已发布的按年锚定分桶键，末桶在次年 1 月 1 日结束；新旧数据查询必须正确。
7. 历史异常布局：不猜测或覆盖已有行；提供可验证、非破坏性检测和显式迁移路径。
8. `timeseries()` 的字符串、对象、`PartitionSpec` 等等价 calendar 声明应构造相同的时间单位与时区；显式传入 `TimeColumn` 的语义不被覆盖。

## 方案比较与取舍

- 已有表分区冲突：静默沿用旧值会误导调用者；原地改元数据会使数据落错位置；因此在有物理分区时抛 `TableSpecConflict`，错误指向 `repartition_to` / `migrate_to`。空表强制更改在同一表锁内判断并更新。
- PostgreSQL 一致性：仅比较当前对象无法保护跨进程；不同策略在已有时间范围内还可能恰好产生相同边界，因此仅检查边界不能判断未来是否一致。选择对已有原生子分区检查边界，在实际写入事务内使用表级事务 advisory 锁串行化、重查，并在父表上以保留名称的恒真 CHECK 约束持久化规范化分区策略的摘要；不创建数据库级控制 schema。旧表首次写入前先验证已有边界，再将调用者声明记录为今后的契约。无可验证边界时拒绝写入。已有数据库级迁移租约继续保护迁移。
- calendar 边界：更换全局锚点会改变已保存的分区键，故保留原键，仅将跨年的多日尾桶结束边界截断到下年起点。对于 PostgreSQL 旧版已创建的越界尾桶，在事务中先核对尾桶越界部分无行，再按需调整其原生边界；存在越界行或无法安全调整时事务回滚并提示显式迁移，不删除或隐式移动业务数据。
- 时间契约：入口先统一解析用户的分区表达，再据规范化类型和时区推导裸字符串 `time`。历史错误契约与调用者曾显式声明的语义可能无法区分，不能仅凭列类型静默覆盖；提供明确检测/重新声明或复制迁移指导，并验证已有数据可以安全导出。
- 已经发生的错误布局无法通过修改元数据恢复。对目录后端 `validate(deep=True)` 增加逐行分区归属核验，报告实际落错的物理文件；重分区必须扫描源全表，主键冲突不能静默丢弃。
- PostgreSQL 的旧子分区名称会去掉负号，使 `-100` 与 `100` 发生同名冲突；过长名称还会被数据库静默截断。新分区对负数保留符号，长名称附完整名称的确定性摘要；已经存在的旧子分区按经过校验的原生边界复用。若旧名称占用了另一个分区的新名称，创建带确定性摘要的安全名称，不移动或覆盖旧表。
- 夏令时回拨会令同一墙上时间出现两次，前拨还可能令桶起点跳过一段墙上时间。目录分区保留已有键，以覆盖这些情况的保守时间范围裁剪；读取旧表时不能继续依赖旧版保存的较窄范围。PostgreSQL 的日内分钟/小时分区在本地时钟变化的日期合并成覆盖整个本地日的原生 RANGE 子分区，裁剪相邻日跨午夜桶避免重叠；其余日期沿用原粒度。旧版已建细粒度子分区时不能直接与整日范围并存，允许绑定、读取和迁移，与新布局冲突的写入明确拒绝并提示迁移，不自动删除、搬动或重写数据。
- 用户确认绝对时刻应统一按 UTC、同时保留业务时区的日历划分。对 `query(date=...)`，无偏移的 `YYYY-MM-DD` 是业务时区的自然日，不先当作 UTC 时刻换算；该自然日的起止分别从业务时区转换为 UTC，不能假定相差固定 24 小时。既有写入值不自动重写。
- 目录后端的旧纯日期路由把日期当作 UTC 午夜，负偏移时区会得到前一天的分区键。直接全局改路由会令历史主键跨文件重复；选择在分区契约中持久化纯日期路由版本，新表使用业务日期，旧表保持旧路由，只有显式迁移可改变版本。迁移默认保留源版本，目标明确指定新版本时才改变；PG 的日期原生路由已按本地日期解释，不将目录后端的路由版本混入 PG 契约摘要。

## 兼容性与边界

- 保留所有公开参数及其默认值；保留此前显式参数被忽略时的警告和调用位置。
- `force_partition=True` 不再允许在有物理分区时变更布局，这是阻止数据错误所必需的行为修正；空表和新目标继续支持。测试及 README/skill 同步。
- PostgreSQL 优先检查既有迁移控制表中的契约，同时验证分区摘要和真实边界。缺乏 iosql 元数据的旧表，有限边界无法唯一确定历史策略，首次声明须由使用者确认后续沿用的是原策略。首次写入增加父表 CHECK 约束，需要表所有者权限；其后可凭摘要识别即使现有边界相同的不同策略。占用保留约束名但定义不是恒真的用户约束不得覆盖。不能推断或安全调整的情况返回可恢复的明确错误，不自行删除或重写数据。
- 旧版已经错误声明 `calendar` 时间契约的表不会凭猜测自动改语义；给出可执行的显式恢复方式。旧版已经混合分区的目录表，深度校验应识别并保留所有物理数据供迁移。
- 本机协作 API 的锁不保护旧版客户端和绕开 iosql 的文件操作；PostgreSQL 外部 SQL 的分区 DDL 依赖 PostgreSQL 原生表锁。

## 实施前复核

检查调用链、并发和迁移后：警告功能应保持原样；目录分区校验必须在锁内且先于任何批次写入；PG 必须同时覆盖绑定与写入时的跨实例竞态；calendar 的运行时和 PG 边界必须共享同一结束计算。每种历史布局都应有无数据丢失的验证或明确的人工迁移边界。

纯日期路由版本补充复核：元数据必须同时支持旧表、尚无分区的空表、显式低层分区对象和跨进程冲突；不能凭日期文本推断旧库版本。迁移默认与原版本一致，显式升级需完整扫描源表并在新目标写入，PG 校验不得因目录文件路由版本误报冲突。
