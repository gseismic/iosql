# iosql UI（可视化管理台）功能定义

> 方法论：product-feature-def-zh（场景先行）。模式：自主模式（既有产品迭代，
> 目标用户与核心问题明确，场景自行挖掘，全部推断显式标记）。
> 本文是 ui-20260823-overview.md 与 ui-20260825-browse-filter-ux.md 的上游依据，
> 用于回答"为什么这轮迭代做这几件事、不做哪几件"。

## 1. 产品定义卡

| 项 | 内容 |
|---|---|
| 一句话定义 | 帮助 **量化研究员与数据工程师** 在 **本地查看、核对、维护 iosql 时序数据库** 的工作流中解决 **"不写代码也能看懂数据、查到目标行、验真回灌结果"** 的问题，通过 **浏览器管理台把契约、分区布局与数据样本可视化并受控维护**，区别于 **命令行 CLI（要记参数、手拼 JSON 条件、输出不直观）和通用 SQLite 客户端（看不懂逻辑表背后的分区/分文件布局，还容易误碰内部元数据）** |
| 产品形态 | 本机 Web 管理台（localhost，默认只读，可选可修改模式） |
| 商业模式 | 暂不考虑（内部工具） |

**关键风险**：无前提红旗。安全边界（不暴露公网）是硬前提，已在现有实现中结构性保障。

## 2. 用户角色

### 角色 1：量化研究员（数据使用方）
- 目标：快速看清一张表里有什么、行情/因子数据质量如何、找到关心的行
- 痛点：每次都要起 Python 进程或拼 CLI 参数才能看一眼数据；毫秒时间戳不可读
- 使用频率：最高 `[假设]`：工作日每天多个短会话

### 角色 2：数据工程师（数据写入方）
- 目标：回灌/落库后验证完整性（有没有、对不对、多少条），排查布局问题
- 痛点：验证靠脚本逐表跑，缺一个"筛选+计数"的可视化闭环
- 使用频率：回灌批次触发，每周数次

### 角色 3：库管理员（运维方，常与前两角色同人）
- 目标：周期性整理存储（compact/清理废弃文件/重分区）
- 痛点：CLI 步骤多、输出不直观，希望有向导式流程
- 使用频率：低频（周/月级）

**完备性自检记录**：
① 现状替代穷尽——Python 脚本→S2/S4/S5/S6 承接；CLI 拼 JSON→S2/S4/S7 承接；
sqlite3 开物理文件→S1 承接；通用客户端（DBeaver/DB4S）→S1 承接；人肉比对→S6 承接。✓
② Top1 主导——S1"看数据"主导合理：可视化管理台的首要价值就是"看"，
DB4S 的默认页签同样是 Browse Data。✓
③ 旅程分段无空白——发现（表清单）→浏览（S1）→筛选（S2-S4）→下钻（S5）→
核数（S6）→带走（S7）→结构诊断（S8）→维护（S9）→回访（刷新/R 键）。✓

**长尾清单（合计 ~3%）**：

| 场景 | 占比 | 第一版承接方式 |
|------|------|--------------|
| 跨表自由 SQL 查询 | ~1% | 简化承接（Query Tab 条件查询）；完整 SQL 后续版本 |
| 编辑/修改单元格数据 | <1% | 不做：时序库 append-only 心智，写路径走 API/CLI `[假设]` |
| 多表并行对比浏览 | <1% | 后续版本 |
| 远程分享只读视图 | <1% | 明确不做：安全模型禁止暴露公网 |
| 时序走势图快览 | 已上线 | Charts Tab（不在本轮迭代范围） |

### 场景卡（供功能推导，仅列关键差异步骤）

- **S1**：打开 UI → 左侧表清单识别目标表 → 进入 Browse → 首屏立即有可读数据 → 连续翻屏扫读
- **S2**：定位目标列 → 直接在该列下方输入精确值 → 条件即刻生效 → 扫读命中行
- **S3**：进入 Browse → 默认最新优先 → 读时间列判断新旧（时间必须可读）
- **S4**：输入比较/范围/多值条件 → 与其他列条件叠加 → 对照计数判断合理性
- **S5**：点击可疑单元格 → 看完整格式化内容 → 复制原值
- **S6**：设好筛选 → 等待计数 → 与预期比对（大表计数要有过程反馈）
- **S7**：保持当前筛选 → 选格式导出 → 拿到文件

## 5. MVP 覆盖对照（本轮迭代 = PLAN-059）

- 场景覆盖：S1–S7 全部由产品功能承接；S8/S9 由既有 Structure/Maintain 承接；
  长尾按 §3 承接方式处理，无空洞。
- 包含功能（新增）：F02、F03、F04、F05（Bug 修复）+ P1：F11、F12、F13
- 第一版明确不做：
  - LIKE 模糊搜索——核心查询算子白名单已冻结，模糊匹配涉及双引擎与分区裁剪
    语义，不宜在 UI 迭代中扩散；文本列裸词先提供精确匹配观察够不够用 `[待决策]`
  - IS NULL 过滤——底层相等比较无法表达 IS NULL，需专门编译路径，跳过
  - 无限滚动懒加载——keyset 分页内存可控，用页大小选择器缓解扫读效率

## 6. 非功能需求（仅列相关项）

- 安全：仅监听 localhost；只读模式下写能力结构性不存在（沿用现有模型）
- 性能：所有数据请求服务端分页/流式，任何表规模下界面不因数据量卡死
  （对标 DB4S 懒加载要解决的问题，用 Web 分页达成同一目标）
- 隐私：数据不出本机

## 7. 假设与开放问题

- [假设] 主要用户主场景是金融时序表（symbol+毫秒时间戳结构），因此"最新优先"
  和"时间可读化"收益最大；若维表浏览为主则 F02 收益下降
- [假设] 90 天 200 次目的性使用的量级与"研究员高频、管理员低频"的角色分布
- [估算] §3 占比为 DB4S 交互类比 + 自省估计，整数档位，待实际使用校验
- [不可估算] 无真实埋点，精确频率不可得，收敛依据为完备性三项自检（已过）
- [待决策] 是否推动核心查询层扩展 LIKE 算子（动冻结接口）——建议暂缓，
  先收集"精确匹配不够用"的真实证据再立项
- [待决策] 时序表默认倒序对"从头检查历史回灌"用户略有不便——建议接受
  （点列头即切正序，成本一行），不做方向记忆以保持行为可预期
