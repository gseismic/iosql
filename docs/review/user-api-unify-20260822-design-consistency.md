# user-api-unify-20260822-design-consistency —— 设计-实现一致性审计

## 定位

本文是对 PLAN-052（用户接口统一与稳定）实施成果的**设计与实现一致性审计**。逐条对照设计文档 `docs/design/user-api-unify-20260822-consolidated.md` 的九项接口设计建议、测试设计与验收基准，核对实际落地代码（commit 范围 `cc5b95d..HEAD`，共 14 个提交），对每处分歧给出"哪边更好"的判定与理由。

审计方法：设计原文逐条检索 + 实现源码逐行比对 + 关键行为实测（含 SQLite 双引号字面量陷阱复现、既有宽容行为取证）。

## 二、关键分歧逐个分析（哪个好）

### 分歧① evolve 语义一的实现机制 —— **实现更优**

- **设计原文**："查询 union 各分区时，旧分区该列以 NULL 投影补齐"（查询期投影）
- **实现**：新分区创建/加列时把新列 ALTER 到旧分区文件（schema 期补列），旧行物理值为 NULL
- **分析**：两者满足同一语义（旧分区读该列为 NULL），但机制上实现严格更优——SQLite 存在双引号字面量陷阱：对缺失列执行 `select "f1"` 会返回字符串 `'f1'` 而非报错（本次审计中实际复现）。查询期投影要求每条 SQL 按各文件 schema 动态改写列清单，任何遗漏即静默读坏数据；物理补列让所有分区的 SELECT 天然安全，segment stats 也能正常纳入新列。设计自身预留了"实施时以源码可达性微调，语义本身不可再开放"的口子。
- **判定：实现优于设计草图**。语义未变，机制规避了一个设计未预见的存储引擎陷阱。

### 分歧② evolve 语义三的声明列冲突规则 —— **实现更优（设计前提失实）**

- **设计原文**："契约已声明的列按声明优先（数据不匹配时写入报错，**即现有行为**）"
- **事实核查**：该括号断言失实。既有测试 `test_segment_mixed_type_stats_remain_conservative` 证明现状是**宽容**的——声明 text 的列写入整数静默成功（SQLite TEXT affinity 转换），且这是被依赖的合法用法（混合类型下 stats 保持保守）。
- **实现的取舍**：只拦截真正危险的方向（文本/blob 写入数值声明列），数字→text 放行。
- **判定：实现优于设计文字**。若照设计文字实现会引入破坏性变更；实现保住兼容性同时仍堵住主要 footgun。偏离及理由已在 OUTCOME 中披露。

### 分歧③ timeseries 签名形态 —— **实现更优**

- **设计草图**：`..., session_column=None, **table_kwargs`（剩余参数通配透传）
- **实现**：全部参数显式声明（partition/segment/order_key/conflict/schema_policy/force_partition + 四个废弃参数）
- **分析**：通配透传的问题——拼写错误静默吞掉、IDE 无法补全、参数演进脆弱；且设计自己要求"废弃参数触发 DeprecationWarning 并等价迁移"，通配形式无法对具名废弃参数做精确警告与迁移映射。
- **判定：实现优于设计草图**。

### 分歧④ select 的 to_dict 默认值 —— **设计内部自相矛盾，实现的取舍正确**

- **设计三节**（正式签名）：`to_dict=False`
- **设计八节片段注释**："返回 dict 行列表 (默认 to_dict)"——暗示默认 dict
- **实现**：保持 `to_dict=False`（非破坏），示例显式传 `to_dict=True`
- **分析**：翻转默认值会让既有调用方（对元组解包/索引）静默变行为，违背本轮"只放宽不破坏"原则。人体工学代价真实存在（裸 `select()` 返回 sqlite3.Row 打印不友好），正确出路是开放问题 2 的方向——新代码示范 `query()` fluent 对象（天然 dict 行），标志位留待未来 major 版本翻转。
- **判定：实现的保守选择正确**。建议将"to_dict 默认值翻转"补记为 v0.4 候选事项。

### 分歧⑤ `rows_seen → rows_received` —— **推迟正确，设计批评仍然成立**

- **设计七**提议更名（兼容别名过渡）；**开放问题 3**倾向 v0.3 统一处理；**PLAN-052** 任务块未纳入。
- **分析**：命名批评有效（"seen" 含糊，实为输入行数）。但本轮已含大量弃用迁移，再叠加字段别名会稀释弃用信息注意力；单独成批迁移成本更低。
- **判定：推迟的决策更好**（批次内聚），设计批评留档待办（OUTCOME 遗留项 #1）。

### 分歧⑥ group_by/select_all "deprecated 后删除" —— **按计划范围正确**

- **设计六**的完整句是长期路线（先弃用后删除）；**PLAN-052 非目标**明确"不移除任何公开符号（全部走兼容别名 + DeprecationWarning）"。
- **判定：本轮实现与计划一致**；删除属于弃用周期完成后的下一版本动作，非偏离。

### 分歧⑦ 流式入口文档收敛 —— **实现有一个小缺口**

- **设计七**："iter_batches 为主形态，iter_rows 说明为其语法糖"
- **现状**：README 流式小节展示了两种形态，但未标注二者的主次/语法糖关系；示例中 `iter_select("*", ...)` 仍用位置参数风格。
- **判定：设计更好**。这是本次审计发现的唯一实质不一致（一行级文档缺口）。

## 三、一致性亮点（实现有增益的点）

1. **op 白名单收口**：设计只要求白名单放构造入口；实现进一步分离展示层用户语言（错误信息展示 `between`）与内部规范形式（`between_and`），归一化/裁剪/编译三层共用同一规范。
2. **range 不反推的不对称**：设计开放问题 1 仅提出问题；实现落成两处一致的代码约束并以注释绑定，防规则漂移。
3. **锁内重读 meta**：设计完全未预见并发维度；review 轮发现并发演进竞争后补强 `_schema_lock` + 进锁重读，并经 A/B 实证（无锁首轮复现缺列 / 真锁 20/20 稳定）。
4. **文档增益**：废弃参数迁移表、合法 op 对照表、动态扩列语义节、导出面分层节，均超出设计最低要求。

## 四、结论与建议

**总体判定：实现与设计高度一致（九项中七项完全一致）。四处偏离全部是实现侧更优或更有据**——机制上规避了设计未预见的 SQLite 双引号字面量陷阱（分歧①）、纠正了设计的事实性错误前提（分歧②）、以显式签名达成设计自己要求的弃用警告能力（分歧③）。设计的价值在方向与语义契约，实现的价值在机制选型，二者互补。

**待办建议**：

1. README 流式小节补一句"`iter_select()` / `iter_rows()` 是 `iter_batches()` 的逐行语法糖"，并将 `iter_select("*", ...)` 示例改为关键字风格（完成设计七最后一块拼图）。
2. 将"select to_dict 默认值翻转（配合 query() fluent 风格推广）"记入 OUTCOME 遗留项，作为 v0.4 候选。
