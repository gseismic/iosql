## 结论

当前主要瓶颈是 **M3 上反复切换六小时 SQLite 文件所产生的提交、连接关闭和 WAL checkpoint 成本**，其次是逐行缓冲调用的协作包装和无用途类型推断。CSV 读取及每文件断点保存不是这个采样窗口的主要耗时。

业务恢复器 `projects/crypto.bn_data_sync/log/kline-resume-20261021-2327.py:145` 传入 `force=True`，跳过了主键覆盖预检查。此前 MIN/MAX 预扫描问题已修复，这次不能再用那个预检查比例解释运行时间。

## 现场证据

被测 PID 3924671、父进程 3924659，Conda Python 实际 PYTHONPATH 指向当前 iosql。CSV 位于 Z1（NTFS），库位于 M3（解析为 `/dev/sdc1`，ext4、USB HDD）。业务导入器 SHA256 与之前一致。

- 约 30 秒、298 个只读 `/proc` 样本中，180 个（60.4%）为 D 状态，CPU 增加 10.89 秒；等待点包括 `folio_wait_bit_common`、`jbd2_log_wait_commit` 和 `rq_qos_wait`。
- 同一窗口访问 559 个不同数据文件，294/298 次只保留 5 个打开的数据文件。库默认缓存就是 5（`iosql/engines/sqlite/table.py:332`），缓存淘汰时同步关闭连接（`:5216`、`:5265`）。
- 相邻 iostat 窗口：M3 平均忙碌率 55.8%，Z1 为 0.63%。CPU 及磁盘等待都有实际成本，并非纯粹顺序吞吐不足。
- Python 栈挂接受 ptrace 权限限制，非交互 sudo 也不可用。未改系统权限或注入进程；没有在线 Python 栈或内核 fsync 级归因。

## 控制回放

保持真实 CSV、主键/schema、完整分区登记和默认 WAL/NORMAL 设置，用独立临时库调用原业务导入函数。整月 43,200 行覆盖 120 个六小时文件，每组 3 轮；整月 schema 对照没有正式文件中的旧数据，M3 仍与线上进程共享磁盘，绝对数字不等同于在线阶段计时。

| 指标 | NVMe 临时库 | M3 临时库、Z1 断点 |
| --- | ---: | ---: |
| 整次导入中位数 | 1.456 秒 | 8.458 秒 |
| 原生 commit，120 次 | 0.079 秒 | 2.378 秒 |
| 原生 close，122 次 | 0.159 秒 | 3.601 秒 |
| CSV 解析 | 0.127 秒 | 0.135 秒 |
| 断点保存 | 0.018 秒 | 0.023 秒 |

M3 的 commit+close 合计约 5.98 秒，占回放总时间约 71%。`stage.write` 是包含部分 commit/close 的父阶段，不能与它们重复相加。M3 单轮耗时 6.69～9.60 秒，存在明显波动。另用 8 个真实分区、2,880 行回放，重复确认 close/commit 的磁盘等待；首次回放的断点也写在 M3，随后补测了与现场一致的 M3/Z1 组合，原始记录全部保留。

最后一个数据库连接关闭时会自动 checkpoint；checkpoint 包含同步与寻道成本，见 [SQLite 官方 WAL 文档](https://sqlite.org/wal.html#automatic_checkpoint)。本次观察到的提交/关闭开销与该机制一致，但没有内核栈证明每一毫秒的来源，不能把全部 commit 时间当成 fsync。

## 两个 CPU 热点

原业务 `export_to_iosql.py:203` 逐行调用 `buf.append(row)`，`iosql/engines/sqlite/table.py:255` 的装饰器让每次 append 都进入协作资源路径。整月 profile 中约 43,479 次 `resource()`、43,725 次 `realpath()`；`iosql/utils/mysqlite/table.py:528` 的全量推断又产生 561,600 次 `suggest_value_type()`。

## 优化方向和完成状态

优先验证将多个币种在同一个六小时桶内的数据合并写入，减少分区打开、提交、关闭的次数；必须保留逐 CSV 完成断点和坏 CSV 校验语义。现有每文件 50,000 行批次仍会拆成约 120 个小分区事务，单纯增大该值不能消除这层成本。可先落地的局部优化是按批次列表 append 和修复重复推断，但不承诺它们让 HDD 获得 NVMe 对照的提速倍数。

8 组共 27 轮回放均通过完整主键集合核验；所有写入只发生在独立临时库/断点目录，结束后清理。线上任务继续执行，未重启、未改配置、未额外写业务库。诊断脚本 Ruff 与差异检查通过，库代码未变，未重复跑已通过的整库回归。采样、代码自查和性能结论复核完成；计划按只读 profile 范围完成，唯一方法调整是挂接受限后采用 `/proc` 加隔离回放。
