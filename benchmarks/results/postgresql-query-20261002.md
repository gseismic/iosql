## 测量边界

- 客户端 RSS 由每次独立工作进程逐批读取 /proc/self/statm，并用 ru_maxrss 覆盖瞬时峰值；包含启动高水位，不计 PostgreSQL 服务端排序/缓存内存。
- 首批时间包含命名游标声明、规划、排序和首次 FETCH；大范围排序可能在首批之前处理大量数据。
- 基准在服务端生成数据，不包含写入性能；所有表随机命名，每个规模结束即删除。
- 计划反映当前版本/统计/缓存。顺序扫描可合理胜过索引，索引/分区效果必须按负载解读。
- 指定 symbol 且有 symbol/time 前缀索引时，单分组 latest 使用 LATERAL LIMIT 1；其他分组使用 DISTINCT ON。
- 多维分组、无索引及跨组历史扫描仍可能较慢，应结合实际计划确定索引。

## 本机结果解读

- 8 组组合均完成行数、截至时点和全量流式排序检查；分区时间窗实际扫描 1/32 个分区。百万到千万行的客户端 RSS 增量约为 12–18 MiB，没有按总行数线性增长；启动高水位影响该指标，不能据此推断批次大小的精确内存倍率。
- 千万行带索引时，平表/分区表的单 symbol 时间窗中位数分别为 0.082/0.230 ms，1000 个指定 symbol 的 latest 分别为 8.03/8.54 ms；实际计划采用 LATERAL 的 Nested Loop + Limit + Index Scan。无复合索引时，该 latest 为 3302.80/4725.37 ms，实际计划使用 DISTINCT ON 的 Unique 和排序。
- 这里两种布局均有 (ts,id) 主键索引，窄时间窗在无 symbol 复合索引时也较快。分区裁剪成立，但分区不保证比平表更快；仅按 symbol、规划开销和多维历史分组均可能受分区数量影响。
- 千万行 (symbol,venue) 多维 asof 在带索引的平表/分区表上仍为 2.24/5.18 秒，保留 DISTINCT ON 路径。这次数据只有一个 venue，不代表更复杂分组数据上的性能。
- 三列有序流式导出的千万行吞吐为约 124.6–134.9 万行/秒，首批约 56.5–384.0 ms。六列全量扫描约 9.1–9.5 秒。该结果对应本次六列合成数据、机器和温/热缓存条件，不作为生产延迟承诺。
